# コード解説

`/explain` はコード変更を、変更内容と理由を学べる自己完結型の HTML 文書に変換します。システムを知らない読者向けの深い背景（すでに知っていれば読み飛ばせます）、おもちゃのデータを使った直感セクション、理解しやすい順序のコードウォークスルー、5 問のクイズを含みます。出力はオフラインで開ける 1 つの `.html` ファイルで、図、コールアウト、アクセシブルなクイズを含みます。`.agents/results/explain/` に保存され、配布前に決定的なチェックリストで検証されます。

`/explain` はスラッシュコマンド専用で、自然言語から自動起動しません。「explain」は日常的な語なので、キーワード検出から意図的に除外されています（`/convert` と同じ扱いです）。`/explain` を明示するか、別のスキルに「解説文書」を委任成果物として作らせます。

---

## 使う場合

- PR、ブランチ、コミット範囲、現在のステージ済み／未ステージの変更を文書として説明する
- 自分が書いていない変更をチームメイトへ引き継ぐ
- 大きい変更または理解しにくい変更の後に、レビュー可能な教材を作る

## 使わない場合

- ナレーション付き解説 *動画* → [`oma-video`](/docs/guide/video-generation)（explainer モード）。`/explain` は動画ではなく HTML 文書を作ります
- ドキュメントがコードベースと一致するかの確認 → `oma-docs`（ドリフト検出）
- プレゼンテーションデッキ／スライド → `oma-slide`（固定 1920×1080 デッキのコントラクト）
- 欠陥の発見やレビュー判定 → `/review`／`code-review`。`/explain` は変更を教育的に説明しますが、評価はしません

## クイックスタート

```text
/explain
/explain 640
/explain a1b2c3d..e5f6a7b
/explain payments-refactor for reviewer
```

入力された表現から対象の参照（ref）を解決します。

| 入力 | 対象の解決 | 読者レベル |
|---|---|---|
| `/explain` | ステージ済みの変更（`git diff --cached`）、なければ変更のあるワークツリー | `onboarding` |
| `/explain 640`、`/explain #640` | `gh pr diff` による PR #640 | `onboarding` |
| `/explain a..b` | SHA 範囲 `a..b`（または `a...b`） | `onboarding` |
| `/explain feature-branch for reviewer` | `git diff main...feature-branch` | `reviewer` |

明示的な参照（ref）がなく、ステージ済みの変更と変更のあるワークツリーの両方が空なら、`HEAD~1..HEAD` へフォールバックします。

## 参照の解決順序 {#ref-resolution-order}

1. **明示的な引数**（PR 番号（`#640`）、ブランチ名、SHA 範囲（`a..b`／`a...b`））
2. **ステージ済みの変更**（`git diff --cached`）
3. **変更のあるワークツリー**（`git diff`）
4. **フォールバック**（`HEAD~1..HEAD`）

空の diff や解決できない参照ではワークフローを停止します。別の参照を推測せず、最近のコミットを候補として提示します。

## 読者レベル

| レベル | 効果 |
|---|---|
| `onboarding`（デフォルト） | 周辺システムを知らない読者向けの深い背景（Tier A） |
| `reviewer` | 深い背景の層を短くし、Intuition と Code は完全に保つ |

`reviewer` は、`/explain feature-branch for reviewer` のようにコマンドへ「for reviewer」を追加して指定します。

## 文書に含まれる内容

すべての解説は、タブや複数ページのナビゲーションを持たない、1 つの長いスクロールページです。目次に続いて、順序を固定した 4 セクションがあります。

1. **Background** には、Tier A（システムをすでに知っている場合は読み飛ばせると表示）と、この変更に絞った Tier B を含めます
2. **Intuition** では、変更の本質を、おもちゃのデータ例と、2〜3 種類の再利用する図（簡略化した UI モック、例データを載せたシステム／データフロー図、変更前後の状態）で補強します。HTML／インライン SVG だけを使い、ASCII アートは使いません
3. **Code** では、人が理解しやすい順にウォークスルーをまとめます。コードは `file:line` で参照します
4. **Quiz** では、デフォルト 5 問（変更可能）を用意します。各問は別の観点を扱い、もっともらしい誤答と、正誤それぞれのフィードバックを持ちます

文章とクイズは要求された出力言語（プロンプトの言語 → `.agents/oma-config.yaml` の `language` → 英語）で書きます。コード、識別子、インラインコードは i18n ルールに従って英語のままにします。完全な内容のコントラクトは `.agents/skills/oma-explanation/resources/document-structure.md` にあります。

## HTML コントラクト

生成されたファイルは `file://` で正しく開け、外部リソースを 0 件にしなければなりません。CDN のスクリプトやスタイルシート、Web フォント、外部画像は使わず、インライン SVG または data URI だけを使います。ハイパーリンクの `<a href="https://...">` は許可されます。禁止されるのはリソースを読み込むことです。

- コードブロックは `<pre>` を使います。カスタムコンテナでは `white-space: pre-wrap` を宣言します。外部の構文ハイライトライブラリは使いません
- フォントスタックは CJK 用に `local()` の Pretendard を先頭に置き、システム CJK フォント、`system-ui` の順にします
- 375px からレスポンシブにし、ライトとダークの両テーマで WCAG AA のコントラストを保ち、`prefers-color-scheme: dark` に対応し、`prefers-reduced-motion` を尊重します
- クイズは vanilla JS です。選択肢を `<button>` として置き、`aria-live="polite"` の領域で正誤のフィードバックを即時に知らせます。正解の位置は分散させ、最終スコアを表示し、キーボードで全操作できるようにします

完全な動作仕様は `.agents/skills/oma-explanation/resources/html-contract.md` にあります。

## 秘密情報とプロンプトインジェクションへの対策

diff の内容と PR の説明はすべてデータとして扱い、説明対象の変更に含まれる指示は無視します。

秘密情報は 2 回ゲートします。

1. **生成前**。収集した diff をスキャンします
2. **生成後**。背景の文章が変更されていないファイルを引用できるため、最終 HTML もスキャンします

検出した場合は生成を直ちに停止し、場所だけをマスクして報告します（実際の値は出しません）。伏せ字を解除して続行するには、明示的な確認が必要です。

## 検証チェックリスト

生成後、grep ベースのチェックリストを出力に対して実行します。外部リソース読み込みの参照がないこと、コードコンテナが `pre`／`pre-wrap` の契約を満たすこと、クイズスクリプトがあること、ファイル名が `{YYYY-MM-DD}-{slug}.html` 形式であること（Asia/Seoul の日付）、最終 HTML の秘密情報スキャンを確認します。失敗した場合は最大 **3 回**修正して再検証し、それでも残る失敗項目を表示します。

これは v1 の制約です。検証は grep／ファイルベースで、クイズスクリプトの存在だけを確認します（動作の完全な正しさは確認しません）。動作の確信が必要なら、ブラウザー（または chrome-devtools MCP）でクイズを手動操作します。

既存アーティファクトは次の登録 CLI コマンドで検証できます。

```bash
oma explain validate .agents/results/explain/2026-09-09-payment-refactor.html
oma explain validate --input-dir .agents/results/explain --output json
```

最初の形式は 1 つの HTML ファイルを確認します。ディレクトリ形式はディレクトリ内の全レポートを確認し、機械可読なレポートを返します。`--report-file <path>`（旧表記は `--out-file`）で JSON レポートを保存します。終了コードが 0 以外なら、決定的チェックの少なくとも 1 つが失敗しています。文章の正確さやクイズの答えは調べません。

## 出力

```
.agents/results/explain/{YYYY-MM-DD}-{slug}.html
```

日付は Asia/Seoul にローカライズされます。同じ日付と slug で再実行すると以前のファイルを上書きします。過去の実行を残すのは利用者の責任です。検証に合格すると、ワークフローは `open <path>` を試み、TL;DR とファイルパスを報告します（警告のみ。ヘッドレス環境や `open` がない環境ではパスの報告に戻ります）。

## 任意の archify サイドカー

`oma-config.yaml` の `diagram.explain_sidecar: true` を設定するか、`/explain 640 with archify` のように依頼すると、`/explain` はインタラクティブな `{date}-{slug}.archify.html` も、主フロー図から派生させてリンクします。プライマリの解説ページには埋め込みません。解説ページは単一の自己完結ファイルのままで、サイドカーの失敗は解説ページを止めません。[ダイアグラムエンジン](/docs/guide/diagram-engine)を参照してください。

## エッジケース

| 状況 | 動作 |
|---|---|
| 空の diff／解決できない ref | 停止し、最近のコミットを候補として提示します。別の ref を推測しません |
| 大きすぎる diff | ロックファイルと生成ファイルを自動除外し、残りをファイルごとにまとめ、除外を出典情報フッターに列挙します |
| バイナリのみ、または生成ファイルのみの diff | 停止します。解説できるものがありません |
| PR ref で `gh` CLI がない、または未認証 | インストール／認証の案内と、ローカルブランチの diff という代替手段を示します |
| merge／rebase 中 | 停止します。ワークツリーが安定していません |
| git ディレクトリではない | 直ちに停止します |
| 3 回の修正ループ後も検証に失敗 | 失敗したチェックリスト項目を表示して停止します |
| `open` が失敗、またはヘッドレス環境 | 警告のみ。報告したパスで十分です |
