# ハーネス評価

`oma harness eval` は、エージェントのモデルを変えずに、候補の OMA ハーネスで固定した対象エージェントの性能が向上するかを測定します。[AI4AI at Test-Time: Strong-to-Weak Capability Transfer via Harnesses](https://arxiv.org/abs/2608.12307) のテスト時評価パターンを応用し、対象モデルを固定してハーネスだけを変え、同じタスクの結果を比較します。

このコマンドが評価する単位は `oma skill eval` より大きくなります。

| コマンド | 対象 | スコアの対象 |
|:--------|:----------|:-------------|
| `oma skill eval` | 1 つの `SKILL.md` 本文 | エージェントの出力 |
| `oma harness eval` | 範囲を絞った `.agents/` オーバーレイ | リポジトリのワークスペースで生成されたファイルと出力 |

「このスキルは役立つか」を知りたい場合は `oma skill eval` を使います。「スキル、ワークフロー、ルール、エージェント指示の組み合わせによって、固定したエージェントがリポジトリタスクをより安定して完了できるか」を知りたい場合は `oma harness eval` を使います。

## 評価モデル

各タスクはペア実験として実行されます。

1. OMA はタスクのフィクスチャを新しいベースラインワークスペースへコピーします。
2. 現在の `agents`、`config`、`rules`、`skills`、`workflows` 定義をそのワークスペースにコピーし、選択したベンダー形式へ投影します。
3. 2 つ目の新しいワークスペースでもセットアップを繰り返し、そこで候補オーバーレイを適用します。
4. 両方の実験群で同じ主エージェント、ベンダールート、プロンプト、書き込み権限、タイムアウトを使います。
5. 決定的なチェックで、生成されたワークスペースと任意のエージェント出力を検査します。

実際のプロジェクトが実験群の作業ディレクトリになることはありません。スコアリング後に一時ワークスペースは削除され、選択したベンダー自身のプロセスサンドボックスが作業ディレクトリ外へのアクセス権限を決めます。

## 候補の構成

候補パスは、部分的な `.agents/` ツリーを含むディレクトリです。

```text
candidate/
└── .agents/
    ├── agents/
    │   └── docs-curator.md
    ├── rules/
    │   └── documentation.md
    ├── skills/
    │   └── project-docs/
    │       └── SKILL.md
    └── workflows/
        └── docs-check.md
```

受け付けられるのは `.agents/agents`、`.agents/rules`、`.agents/skills`、`.agents/workflows` の下にあるファイルだけです。フック、評価フィクスチャ、状態、結果、設定ファイル、シンボリックリンク、ベンダーエージェントのバリアントは拒否されます。`model`、`tools`、`effort`、実行上限など、保護されたエージェントの frontmatter フィールドはベースラインと一致しなければなりません。スコアリング前に実行中のエージェントが保護された `.agents/` 定義を変更した場合も、その実験群は失敗します。

## スイート形式

スイートは 1 つの YAML ファイルと、タスクごとに 1 つのフィクスチャディレクトリで構成します。

```text
harness-eval/
├── suite.yaml
└── fixtures/
    ├── stale-api-doc/
    │   ├── docs/api.md
    │   └── src/session.ts
    └── missing-guide/
        ├── docs/
        └── src/feature.ts
```

```yaml
schema_version: 1
id: docs-harness
agent: docs-curator
tasks:
  - id: stale-api-doc
    prompt: Update the API documentation to match the implementation.
    workspace: fixtures/stale-api-doc
    weight: 1
    checks:
      - type: file_contains
        path: docs/api.md
        value: openSession
      - type: file_not_contains
        path: docs/api.md
        value: createSession
```

タスク ID は一意でなければなりません。フィクスチャパスとチェックパスは、プロジェクトとタスクのワークスペース内にとどめます。フィクスチャにシンボリックリンク、`.agents`、`.codex`、`.claude`、ベンダーのスキルディレクトリ、ルートのエージェント指示ファイルなど、エージェントハーネスの制御面を含めてはいけません。これにより、タスクデータがどちらの実験群の制御ハーネスも隠せないようにします。

`node_modules` や `.venv` などの生成された依存ディレクトリは、ベースラインハーネスからコピーされません。決定的なヘルパーのソースと依存関係マニフェストをスキルにコミットし、チェックに必要なランタイム依存関係はタスクフィクスチャで準備します。

### チェックの種類

| 種類 | フィールド | 合格条件 |
|:-----|:-------|:---------------|
| `file_exists` | `path` | 実験群の完了後にパスが存在する。 |
| `file_not_exists` | `path` | パスが存在しない。 |
| `file_contains` | `path`、`value` | ファイルが存在し、値を含む。 |
| `file_not_contains` | `path`、`value` | ファイルが存在し、値を含まない。 |
| `output_contains` | `value` | 取得したエージェント出力が値を含む。 |
| `output_not_contains` | `value` | 取得したエージェント出力が値を含まない。 |

アーティファクトチェックは意図的に決定的です。評価対象のエージェントがスクリプトやテストを編集して評価を無効にできるため、初版は変更可能なパッケージスクリプトを判定プログラムとして実行しません。

## 実行と記録

ライブモードはタスクごとに 2 つのディスパッチを行い、コストのプレビューを表示して確認を求めます。

```bash
oma harness eval \
  --suite harness-eval/suite.yaml \
  --candidate candidate \
  --live --record
```

成功した実行のレポートには、ベースラインと候補のペアスコア、改善幅（lift）、回帰数、`pass` または `insufficient` などの判定が含まれます。スイート、ベースライン定義、候補オーバーレイ、プロンプト、フィクスチャ、チェックを変更した場合は、新しいライブ実行を記録してください。古い `_runs` ファイルはハッシュで拒否されます。

非対話式の実行には `--yes` を使います。`--timeout-minutes` を指定すると、各実験群に同じ実時間上限を設定できます。ライブ実行を使えるのは、選択したベンダーがプロジェクトのワークスペースを基準にハーネスファイルを見つけた場合だけです。ベースラインからグローバルにインストールされた候補が見える可能性があるため、OMA は HOME を基準にした探索を拒否します。

`--record` はスイートの隣の `_runs/` にハッシュ付き JSON 記録を書きます。記録は次の 3 つの入力に結果を結び付けます。

- スイート、プロンプト、チェック、フィクスチャの内容
- 現在のベースラインハーネス定義
- 候補オーバーレイの内容

モックモードがデフォルトで、モデルを呼び出しません。3 つのハッシュがすべて一致する場合だけ記録を再生します。

```bash
oma harness eval \
  --suite harness-eval/suite.yaml \
  --candidate candidate \
  --mock --require-coverage
```

## メトリクスと判定ゲート

すべてのチェックに合格したタスクだけが合格します。スコアはペアタスクの加重平均です。

```text
lift = candidateScore - baselineScore
```

OMA は次も報告します。

- `corrected tasks`: ベースラインが失敗し、候補が合格したタスク
- `regressed tasks`: ベースラインが合格し、候補が失敗したタスク
- `coverage`: スコア化できるペアタスクが少なくとも 5 つ必要

改善幅（lift）が 5 パーセントポイント以上で、回帰がなければ候補は合格します。回帰が 1 つでもあれば候補は失敗します。0 以上 5 ポイント未満の改善幅は警告になり、ペアタスクが 5 未満なら `insufficient` 判定になります。CI でカバレッジ不足を終了コード 0 以外にするには `--require-coverage` を追加します。実験群が欠けている場合、記録のハッシュが古い場合、決定的なチェックが未完了の場合、スコアは根拠になりません。

## 現在の境界

これは評価の基盤であり、ハーネスの自動最適化ではありません。作成者は外部で候補オーバーレイを作り、このコマンドを受け入れゲートとして使えます。独立した非公開の最終テストスイート、繰り返しの確率的試行、信頼済みの外部テストランナー、トークン集計、ネストしたサブエージェント呼び出しへの強制モデル固定、`harness opt` の自動ループは、現在のコマンドには含まれません。ネスト呼び出しの固定が実装されるまでは、1 つの固定モデルを測るスイートで、設定済みの別ロールを起動する候補ワークフローを避けてください。
